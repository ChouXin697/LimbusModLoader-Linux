# 4. 模组格式与取证

本文讲的是加载器所消费的那些文件**里面装的是什么**，以及出问题时怎么查看。移植没有改动任何
格式；这里是[文档 3](03-疑难排查.md)的背景知识。

`LimbusCompanyMods/` 里有三类东西：

| 文件 | 是什么 |
| --- | --- |
| `*.zip` | Lunartique「安装包」——一棵同时含 `Installation/` 与 `Uninstallation/` 两份 `__data` 的目录树 |
| `*.carra` / `*.carra2` | 压缩过的**增量**：只含与原版不同的对象 |
| `*.bank` | FMOD 音频 bank（事件元数据）或 `.assets.bank`（采样数据） |

---

## `.carra` 与 `.carra2`

两者都是 **ZIP 压缩包**，但不是能直接解压来读的那种：

```
<A>/<path_id>.<type_index>      ← .carra2 的条目
<A>/<path_id>                   ← 老 .carra 的条目（无类型后缀）
```

- `<A>` 是目标缓存 bundle 的**外层**哈希。由于 `extract_assets()` 会把 `<A>/<B>/<file>` 拍平成
  `<A>/<file>`，**单凭 `<A>` 就决定了 mod 打到哪个 bundle**；内层 `<B>` 被丢弃。任何「改内层
  文件夹名」的建议在这套加载器上都是空操作。
- `<type_index>` 是**该 bundle 自己类型表**的下标——它**不是**全局类型 id，不能跨 bundle 翻译。
  老 `.carra` 条目省略它，加载器便当作 `-1`，跳过类型检查。
- 每个条目的**内容是 XZ 流**（魔数 `\xfd7zXZ\x00`）。解压后是：

  ```
  u32LE 名字长度 | 对象名 | 对齐到 4 字节的填充 | 对象原始字节
  ```

> **坑：没解压就别在 `.carra*` 里扫字符串。** 条目是 LZMA 压缩的，扫 ZIP 条目字节得到的是噪声。
> 「这个包里没有文本」这类结论必须从**解压后的对象名与载荷**得出，而不是压缩字节。我们曾犯过
> 正好这个错误，后来不得不撤回结论。

### `.zip` 是怎么变成 `.carra2` 的

`compress_lunartique_mod()` 就是一个增量编码器：

1. 找到同时含 `Installation/` 与 `Uninstallation/` 的根目录。
2. 对 `Uninstallation/**/__data` 下每个对象，对其原始字节取哈希（`xxh128`）。
3. 对 `Installation/` 下的对应对象，**仅当**字节不同或是新对象时，才写入一个条目。
4. 每个写入的条目为 `lzma.compress(data, preset=9, FORMAT_XZ)`。

所以 `.carra2` 只含改动过的对象——这也正是一个坏条目可以从里面删掉的原因（原版对象原地保留，
见[文档 3](03-疑难排查.md#游戏启动后立刻崩溃)）。

`detect_lunartique_mods()` 在启动时做这个转换，然后**删除 `.zip`**。下载来的每一份都请自己留底。

### 查看一个 `.carra2`

```python
import lzma, struct, zipfile

with zipfile.ZipFile("mod.carra2") as z:
    for entry in z.namelist():
        bundle_hash, _, rest = entry.partition("/")
        pid, _, type_idx = rest.partition(".")
        raw = lzma.decompress(z.read(entry))          # FORMAT_XZ
        n = struct.unpack_from("<I", raw, 0)[0]
        name = raw[4:4 + n].split(b"\x00")[0].decode("utf8", "replace")
        print(f"{bundle_hash[:8]}  pid={pid:<8} type={type_idx or '-':<3} len={len(raw):>9}  {name}")
```

这样读对象名，是看清一个包到底动了什么的最快办法——名字就是游戏自己的资源名
（`idle`、`skill3_10`、`10812_normal_profile`、`sactx-0-2048x2048-…`）。

## mod 重叠

多个 mod 可以打同一个 bundle；加载器按它看到的顺序施加
（`sorted(..., key=mod_file_size, reverse=True)`——**文件最大的先来**）。后嫁接的（更小的文件）
在携带相同 `path_id` 时会覆盖先前的。

有两个值得知道的后果：

- 只动少数对象的 mod，实际上是叠在更大那个之上的补丁；大包的其他对象会存活。
- 两个都重写**同一个**对象的包无法共存——一个会静默胜出，而胜负由**文件大小**而非名字决定。

实践上有用的策略是**把各包最好的部分合起来**，而不是整体装某一个：从一个包取更新／更好的资源，
保留另一个包没有覆盖的对象。若某个包因为一个坏对象而崩溃（比如类型树不兼容），只删掉那一个条目，
其余部分就能与别的包共存。

## 外观包的结构

一个角色皮肤包并不是「只有贴图」。典型内容：

- **Sprite / Texture2D / SpriteRenderer**，外加 `SpriteAtlas` 数据（`<name>` 与 `<name>.atlas`）
  ——插图本体。
- **AnimationClip**（`*_Default` 待机、`*_Move`）与 **PlayableDirector** 时间轴——待机插图是被
  AnimationClip 在 Timeline 上**逐帧切出来**的，不是一张静态图。这就是为什么「只改待机插图」必然
  会连带 Sprite／图集／Clip／Director／Transform 一起换，看起来像把动作也改了。
- **Transform**——这套外观自己的骨架／挂点。
- 一个**角色外观控制器 MonoBehaviour**，它同时还挂大招（特殊技）特效钩子：`spEffects`（指向特效
  对象的 PPtr 列表）、`spSkillReadyEffect` / `spSkillReadyEffect_Burn`、`OverrideDeadTimeline`，
  以及外观字段 `material_Current` / `material_Future`、`OverrideSprite`、`afterimageTrails`。

最后一项正是老包最常崩的地方：自该包导出以来，这个控制器的**类型树**可能新增了字段。见
[文档 3 第 3 类](03-疑难排查.md#3-monobehaviour-类型树缺字段)。

## 文本与字色在哪里（以及为什么没人做只有颜色的 mod）

游戏内台词由 **TextMeshPro** 用运行时的 `Font` 资源与 `Material` 绘制。因此台词颜色只可能来自
两处：

1. **字符串内嵌的富文本标签**——本地化文本里的 `<color=#RRGGBB>`，而本地化文本存在 `TextAsset`
   （本地化表）里；以及
2. **`Font`/`Material` 的默认色与描边**。

这两者都不在语音 bank 里，也不在外观包里——这正是「带改图的外观包不会改变台词颜色」的原因。
要发布一个颜色 mod，你只能：

- 改全局的 `Font`/`Material`（会波及**所有**文字与 UI，通常不是想要的效果），或者
- 在本地化表里逐句塞 `<color=…>` 标签（字符串极多，且随游戏更新极易失效）。

这个成本就是颜色改动通常是本地／私服的小调整、而非公开发布的原因。

## 音频 bank

mod 音频文件放到 `FMODBuilds/Desktop/`。FMOD 把每个 bank 拆成两个文件：

- `<name>.bank`——事件元数据（RIFF `FEV FMT` 容器），
- `<name>.assets.bank`——采样数据（`FSB5` 块）。

两者都是 RIFF 容器，且可能含**不止一个 `FSB5` 块**。语音 bank 是按**赛季／内容单元**组织的，
不是按角色分——单个 `Voice_Default_<S><part>.assets.bank` 里混着很多说话人，这就是「良秀的 bank
里为什么还有另外四个人」的答案。

### 读 FSB5

`FSB5` 头布局（小端；头 60 字节，即 `0x3C`）：

```
'FSB5' | version | numSamples | sampleHeaderSize | nameTableSize | dataSize | mode | hash…
```

名字表从 `偏移 + 60 + sampleHeaderSize` 开始，长 `nameTableSize` 字节。`mode` 字段标识编码——
`15` = Vorbis，`16` = FADPCM。

**工具坑。** `ffmpeg` 的 `fsb` 解复用器只支持到 **FSB4**，遇到 FSB5 会直接失败——包括 Flatpak
GNOME runtime 里自带那个构建。请改用 **vgmstream-cli**（`-i` 看名字／编码，`-S 0` 批量导出）。

### 对比原版与实际 mod 版的 bank

两个**正交**的度量，缺一不可：

- **波形相关度（先做时长归一化）** → 反映**音色**（嗓子）是否变了。
- **包络相关度** → 反映**节奏／断句**是否变了。

相关之前**必须先归一化时长**。几毫秒的长度差就会把波形相关度从 ~1.0 拉到 ~0.6，从而得出「它变了」
的错误判断。

```python
import numpy as np

def resample(a, n=4096):
    return np.interp(np.linspace(0, len(a) - 1, n), np.arange(len(a)), a).astype(np.float32)

def ncc(a, b):
    a = resample(a); b = resample(b)
    a = a - a.mean(); b = b - b.mean()
    denom = float((a * a).sum()) * float((b * b).sum())
    return float((a * b).sum()) / np.sqrt(denom) if denom > 0 else 0.0
```

解读：波形 ≈ 1.0 → 同一段录音（可能只是重编码）；波形低但包络高 → 同一段表演，换了嗓子；两者都低
→ 是另一段录音。

最后，务必确认你是在**同类之间**比较：mod 版与原版 bank 必须有一致的**索引 → 名字映射**。若有名字
缺失或错位，所有按名的比较都无意义。
