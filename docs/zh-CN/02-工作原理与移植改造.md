# 2. 工作原理，与移植改了什么

## 管线全貌

对于资源类 mod，加载器**从不碰游戏安装目录**。Limbus 把 bundle 放在 Unity 的
**Addressables 缓存**里，加载器在启动时给这些缓存副本打补丁。

```
Steam 启动项
  └─ run-linux.sh …main.py %command%
       ├─ cleanup_assets()            把 __original 还原回 __data，把 *.bank.bak 还原回 *.bank
       ├─ detect_lunartique_mods()    *.zip  →  *.carra2   （原 zip 被删除）
       ├─ extract_assets()            把每个 *.carra* 解压到临时目录，并拍平层级
       ├─ patch_assets()              对每个缓存 bundle：备份、嫁接对象、写回
       ├─ sound.replace_sound()       把 *.bank 覆盖到游戏音频目录（保留 .bak）
       └─ subprocess.call(sys.argv[1:])   启动游戏，阻塞直到游戏退出
       └─ atexit → cleanup_assets()   还原全部改动
```

有两点决定了移植工作的绝大部分：

- **bundle 按哈希匹配。** 一个缓存 bundle 位于
  `LocalLow/Unity/ProjectMoon_LimbusCompany/<A>/<B>/__data`。`.carra2` 里的条目名为
  `<A>/<path_id>.<type_id>`，而加载器**只匹配外层 `<A>`**。mod 里 `<A>` 下的任何东西，都会按
  `path_id` 嫁接到文件夹名等于 `<A>` 的那个 bundle 里。
- **mod 本身与平台无关。** Lunartique 的 `Installation/`+`Uninstallation/` 布局、`.carra`/`.carra2`
  的对象数据块、`.bank` 文件，全都是纯数据。真正不跨平台的是**加载器自己的路径与进程处理**——
  这就是移植的全部。

## 移植改了什么

`main.py` 与 `compress.py` 原封不动：核心打补丁逻辑是纯 Python + UnityPy，在哪都能跑。
Windows 专有代码只存在于三个文件里——它们分别 `import winreg`、读 `APPDATA`、调 `tasklist`。

### 新增文件：`platform_paths.py`

用一套 Linux 感知的实现取代所有 Windows API 查询。

| 函数 | 作用 |
| --- | --- |
| `steam_roots()` | 候选 Steam 安装位置，最可能的在前：Windows 上读注册表；Linux 上依次为 `~/.steam/steam`、`~/.local/share/Steam`、Flatpak 路径、`/usr/share/steam` |
| `library_roots()` | 所有 Steam 库：上述根目录本身，加上 `libraryfolders.vdf` 里的每个 `"path"`，去重 |
| `find_game_dir()` | 第一个包含 `steamapps/common/Limbus Company/LimbusCompany.exe` 的库；支持 `$LIMBUS_GAME_DIR` 覆盖 |
| `find_prefix()` | `steamapps/compatdata/1973530/pfx`——Proton 前缀 |
| `get_appdata()` | 若设置了 `$APPDATA` 就用它，否则取第一个 `pfx/drive_c/users/*/AppData/Roaming` |
| `is_windows()` | `os.name == "nt"` |

优先级很重要：`$APPDATA` 优先于前缀探测，因此同一份代码在 Proton 内部（`APPDATA` 已设置）和
裸宿主机（未设置）上都能工作。

### 每处改动为什么必要

1. **`winreg` → `platform_paths`（致命，且发生在 import 阶段）。** `import winreg` 在 Linux 上抛
   `ModuleNotFoundError`。由于 `sound.py` 在模块层 import 它、而 `main.py` 又 import `sound`，
   加载器在开始打补丁之前就死了——唯一的症状是日志停在探测完 `Limbus Company` 之后就没了。

2. **`APPDATA` → 由前缀推导的 AppData（致命，且是静默的）。** 宿主机上 `os.getenv("APPDATA")`
   返回 `None`，于是 `bundle_data_paths()` 会执行 `os.path.join(None, …)` 抛 `TypeError`，
   而 `get_mod_folder()` 直接抛 `APPDATA not found`。游戏**自己**是有 `APPDATA` 的——在它自己的
   前缀里——所以正确的来源是 `pfx/drive_c/users/*/AppData/Roaming`，也正因如此，放进那个文件夹的
   东西才能被游戏看到。

3. **写死的 Windows 路径 → `os.path.join` 组件列表。** `r"steamapps\common\…"` 在 Linux 上只是
   一个路径片段。拆成组件交给 `os.path.join`，两个平台都能拼出正确路径。

4. **`patch_bundle_asset` 里 `return` → `continue`（上游潜藏 bug）。** 当某个 bundle 含多个
   serialized file 时，原实现会在第一个非 `SerializedFile` 处中止整个函数。我们在迭代中撞到了这点；
   修法就一个词。值得提回上游。

## 2. 不靠 tasklist 也能还原资产

这部分在 Linux 上的差异是**概念性的**，不只是换个路径。

**轮询为什么存在。** `sound_replace_thread()` 拷完 bank 之后，在 Windows 上会靠轮询
`tasklist /FI "IMAGENAME eq LimbusCompany.exe"` 等游戏退出；进程一消失，就还原音频 bank **以及**
打过补丁的资产。这段轮询是还原逻辑里唯一与 Windows 绑死的部分。

**由什么替代。** 启动项是 `"/…/run-linux.sh" %command%`，所以 `%command%` 作为 `sys.argv[1:]`
传进来，`main.py` 调 `subprocess.call(sys.argv[1:])`——它会**一直阻塞到游戏退出**。随后 `atexit`
处理器执行 `cleanup_assets()`，同时还原 `__data` 与 `.bank`。结果相同，不需要轮询，也不依赖任何
在 Linux 上不存在的工具。

这就是为什么移植做了两件事：

- 让 `is_game_running()` 在 Linux 上返回 `False`（监视循环是 Windows 专有的事）；
- 以及在 `sound_replace_thread` 的监视段开头提前 return（拷贝本身照旧执行）。

拷贝动作在两端都照做——只有「等游戏、再还原」这个尾部是 Windows 专有。

> 后果：既然还原是靠加载器进程退出驱动的，那么**杀掉加载器**（或游戏硬崩、把父进程一起带走）
> 就可能留下打过补丁的 `__data`。该故障模式见[文档 3](03-疑难排查.md#缓存残留打补丁后的-__data-没还原)。

## 移植**故意没做**的事

- **不碰 `main.exe`。** `main.spec`（PyInstaller）与 `install_deps.ps1`（PowerShell）都是 Windows
  专有的构建工具。Linux 上直接从 venv 跑源码，没有需要冻结的东西。
- **不搞 gamescope／沙箱之类的花招。** 加载器就是一个普通用户进程，Proton 那一侧交给 Steam。
  这样 `stdout` 和 `log.txt` 都可读——而这正是「移植」相对「把 `main.exe` 塞进前缀里跑」的全部意义。
- **不改任何文件格式。** `.carra`、`.carra2`、`.bank` 都没被移植改动；它们的坑见
  [文档 4](04-模组格式与取证.md)。

## 相关

- 上游假定加载器在 Windows 上还可能**自己启动**游戏。在 Linux 上，`%command%` 是游戏如何启动的唯一
  真相来源——任何地方都不要写死 `LimbusCompany.exe`。
- 若要新增需要游戏目录的功能，请用 `platform_paths.find_game_dir()`，不要另起一套推导逻辑；
  Windows/Linux/Flatpak 的知识只允许存在于这一个地方。
