# 3. 疑难排查

下面每一条都是我们真实遇到过的。每条都按**现象 → 诊断 → 修复**的顺序写——因为你能拿到手的
就是现象。

## 先看哪里

| 文件 | 内容 |
| --- | --- |
| `<AppData>/Roaming/LimbusCompanyMods/log.txt` | 加载器做的一切：转换、解压、逐对象打补丁、校验摘要 |
| `<AppData>/LocalLow/ProjectMoon/LimbusCompany/Player.log` | Unity／游戏侧报错与崩溃栈 |
| `<AppData>/LocalLow/Unity/ProjectMoon_LimbusCompany/<A>/<B>/` | 缓存 bundle：`__data`（在用）与 `__original`（打补丁前的备份，仅在打补丁状态下存在） |

这里的 `<AppData>` 指
`<库>/steamapps/compatdata/1973530/pfx/drive_c/users/steamuser/AppData`。

两个能省大量时间的习惯：

- 头几次启动时，另开一个终端 `tail -f log.txt`。
- 游戏崩溃时，先读 `Player.log` 的**末尾**——最后一个 `Crash!!!` 块会点名出问题的 bundle。

## 加载器毫无反应／一闪而过

### `ModuleNotFoundError: No module named 'winreg'`

**现象。** `log.txt` 在探测完 `Limbus Company` 之后就停了，或者 Steam 弹出一个转瞬即逝的控制台。
手动运行 `venv-linux/bin/python main.py` 能看到 traceback。

**原因。** 你在跑**上游**源码。`sound.py` 在模块层 `import winreg`，而 `main.py` 又 import 了
`sound`，所以失败发生在任何打补丁动作之前。

**修复。** 用 `loader/` 里移植过的文件。`winreg` 的 import 已移除；`sound.py` 改为从
`platform_paths` 导入 `find_game_dir, is_windows`。

### `Exception: APPDATA not found`，或 `bundle_data_paths` 里抛 `TypeError: ... NoneType`

**现象。** 加载器能启动，但一去找 mod 目录或缓存就死。

**原因。** 上游读的是 `os.getenv("APPDATA")`，宿主机上没有这个变量。游戏的 AppData 在
**Proton 前缀内部**，不在宿主环境里。

**修复。** 同上——移植版从前缀推导 AppData。手动运行加载器时也可以显式指定：

```bash
APPDATA="$PREFIX/drive_c/users/steamuser/AppData/Roaming" venv-linux/bin/python main.py echo
```

### 启动项看着没问题，Steam 却只开了个空控制台、游戏没起来

**现象。** 一个终端窗口闪一下就关了，游戏始终不启动。

**原因。** 漏了 `%command%`，于是 `main.py` 没有可执行的命令（`len(sys.argv) < 2` → 退出码 1）；
或者脚本路径没有加引号／没有可执行权限。

**修复。** 按顺序检查：

```bash
chmod +x loader/run-linux.sh          # 必须有可执行权限
# 启动选项里要一字不差地是：
"/绝对路径/loader/run-linux.sh" %command%
```

再手动确认脚本能找到它的 venv：

```bash
echo "/绝对路径/loader/run-linux.sh" && ls -l loader/venv-linux/bin/python
```

### 游戏起来了，但 mod 没生效

**现象。** 游戏正常运行，`log.txt` 显示在打补丁，但游戏里没有任何变化。

这几乎总是**静默空操作**：mod 指向的 bundle 哈希已经不存在了。见
[mod 装了却毫无变化（静默空操作）](#mod-装了却毫无变化静默空操作)。

## 开始按钮按不了

**现象。** 游戏界面打开了，其他按钮都有反应，但**开始**按钮点了像死的一样。

这**不是 mod 问题**，也是最常被误判的一类故障。

**诊断。**

```bash
tail -50 "$PREFIX/drive_c/users/steamuser/AppData/LocalLow/ProjectMoon/LimbusCompany/Player.log"
```

如果反复刷 `Not Initialize Addressable`，说明 Addressables 系统初始化失败。这是**网络**问题，
不是打补丁的问题。进一步确认：

```bash
# 能解析，但 443/80 超时 => 你的网络到该 CDN 不通
getent hosts download.limbuscompanycdn.org
curl -sS -m 5 -o /dev/null -w '%{http_code}\n' https://download.limbuscompanycdn.org
```

**原因。** `StreamingAssets/aa/settings.json` 里 `m_DisableCatalogUpdateOnStart = false`，所以游戏
**每次启动都要拉一次远端 catalog**。若 `LocalLow/ProjectMoon/LimbusCompany/com.unity.addressables/`
不存在（没有本地回退），同时 CDN 不可达，Addressables 初始化就会失败，开始按钮的点击处理
始终走不完。

**修复。** 让 `download.limbuscompanycdn.org` 可达。需要梯子——而且必须是 **TUN／全局模式**，
因为游戏跑在 Proton 里，**看不到 Linux 的 `http_proxy` 环境变量**。只改 DNS 无效。由于每次启动
都会校验，**每次启动都得把梯子挂着**；一旦连上，本地缓存目录会被重新建立。

## 缓存残留：打补丁后的 __data 没还原

**现象。** 即使你把 mod 移走了，游戏里仍像打了补丁；或者拿「干净基线」去比对时得出离谱的结论
（例如明明改了成百上千个对象，却算出只改了几处）。

**原因。** `patch.py` 会把 `__data` 挪成 `__original`，再写入打过补丁的 `__data`，退出时还原。
如果游戏被强杀，或加载器启动时的清理被打断，缓存就会**停在打过补丁的状态**，**且 `__original`
仍在**。此时任何以当前 `__data` 为基线的比对，基线都是被污染的。

**诊断。** 对每个缓存 bundle 目录：

- `__original` 是否还存在？（在一次正常的、已结束的运行之后它不应存在。）
- `__data` 是否明显偏大？

**修复。** 把被污染的 `__data` 挪开，换回真正的原版：

```bash
for d in "$PREFIX"/drive_c/users/*/AppData/LocalLow/Unity/ProjectMoon_LimbusCompany/*/*/; do
    if [ -f "$d/__original" ]; then
        mv -f "$d/__data" "$d/__data.polluted.bak"
        mv -f "$d/__original" "$d/__data"
    fi
done
```

下次启动就会从真正干净的基线重新打补丁。对于任何你打算**采信**的比对，另外准备一份
**确认无误的原版**（重新下载或干净的备份）作为参照——`__original` 用起来方便，但只有在上一次
运行正常退出时才可信。

## 游戏启动后立刻崩溃

**现象。** 游戏能起来（或在加载战斗／某个角色时崩），`Player.log` 末尾是一段 `Crash!!!`。典型
特征：

```
The image data of Texture '<name>' has an unexpected size (expected N, got 0)
The file 'archive:/CAB-<hash>/CAB-<hash>' is corrupted!
[Position out of bounds!]
```

有三类**完全不同**的根因都会产生这一族报错。先判断你属于哪一类：

### 1. bundle 哈希过期（mod 指向已不存在的 bundle）

这不会崩溃，列在这里只为对照——它在 `log.txt` 里表现为「找不到该 bundle」，游戏则毫无变化。
见下一节。

### 2. 旧序列化布局（载荷字节层面不兼容）

**诊断。** 对 mod 里某个 `Texture2D` 条目，把它解压（`lzma.decompress(data, format=FORMAT_XZ)`），
然后比对 `m_Name` 之后紧跟的三元组 `[m_ForcedFallbackFormat, m_Width, m_Height]` 与**原版**同
`path_id` 对象：

- 完全一致 → 布局兼容；
- **整体偏移一位 int** → 该 mod 是针对更早的 Unity／游戏布局导出的。**不要装**，重定向也救不了。

2024 年做的 mod 是常见此类；针对当前构建重做的 mod 则逐字段一致。

**修复。** 卸载该 mod（把文件移出 `LimbusCompanyMods/`）再重启——缓存会从 `__original` 自愈。

### 3. MonoBehaviour 类型树缺字段

**诊断。** 类型索引与 `path_id`「看起来匹配」，于是加载器照常嫁接——但该对象是针对**更旧的类型
树**导出的。例：某个外观控制器脚本只有 58 字段／276 B，而当前游戏是 64 字段／340 B（某次赛季
更新新增了 `spEffects: vector<PPtr<GameObject>>`，5 个元素 = 64 B）。游戏随后按当前类型树读到
对象末尾之外，报出同样的 `corrupted! [Position out of bounds!]` 并崩溃。

**类型索引匹配 ≠ 格式兼容。** 判据是比对**类型树**：对 mod 用到的每个 type index，递归遍历
`serialized_file.types[idx].nodes`（含 `m_Children`），比较原版与 mod 的节点串。只要有一个索引不同，
就足以崩掉一个对象。

更省事的直查：遍历**嫁接后**包里每个对象并试着读，把失败的报出来：

```python
for path_id, obj in serialized_file.objects.items():
    try:
        obj.read()
    except Exception as e:
        print("unreadable", path_id, e)   # 例如 EOFError: read_length out of bounds
```

在 mod 自己的包里能正常读、嫁接后却失败的对象，就是不兼容的那些。

**修复。** 把该条目从 `.carra2` 里**删掉**（保留原版对象）。风险最低、可完全回滚；上述例子里是
零损失改动。

### 4. 流式贴图指向缺失的 `.resS`

**诊断。** 某些 `Texture2D`（class 28）的 `m_StreamData.path` 非空，像素存在外部的
`archive:/CAB-xxx/….resS` 里。`.carra2` **只携带对象的原始字节**，无法携带外部 `.resS`。若该流式
切片 `offset + size` 落在目标 bundle 自身 `resS` 的范围之外，或它引用的 resS 根本不在包里，嫁接后
的 bundle 就会损坏。

转换前必查：读每个 `Texture2D` 的 `m_StreamData`，与包内实际存在的 `*.resS` 条目长度比对。
若贴图是**内联**的（`m_StreamData.size == 0` 且 `m_ImageData` 非空），则安全。

**修复。** 两个办法，按优先级：

1. **剔掉坏条目**——前提它是**被修改**的对象，且存在同 `path_id` 的自洽原版：游戏继续用原版贴图，
   其余改动照常生效。（若坏贴图是**新增**对象则无原版可回退，此招无效。）
2. **换一个内联打法的包。** 同样的美术资源、不同的导出方式——贴图放在 `m_ImageData` 里的 mod 能被
   `.carra2` 完整携带。

这是**缺资源**问题，不是**格式**问题——两者彼此独立，也可能同时出现。

### 定位是哪个 mod 导致崩溃

1. 从 `Player.log` 最后一个 `Crash!!!` 块里取出 `CAB-<hash>` 名字。
2. 在缓存里搜它，找到对应的 bundle 目录：

   ```bash
   grep -rl "CAB-<hash>" "$PREFIX"/drive_c/users/*/AppData/LocalLow/Unity/ProjectMoon_LimbusCompany/ 2>/dev/null
   ```

3. bundle 目录名（`<A>`）就告诉你哪个 mod 的条目指向了它——每个 `.carra2` 条目都以这个 `<A>` 开头。

## mod 装了却毫无变化（静默空操作）

**现象。** 不崩溃。`log.txt` 显示 mod 被解压了，但它的对象没有对应的 `Patching`／`Loading` 行——
或者打补丁跑了，游戏里却肉眼无变化。

**原因。** 第三方站点下的老 mod 把目标 bundle 哈希 `<A>` 写死为制作时的值。游戏**每次更新都会重算
bundle 哈希**，于是 `<A>` 与任何缓存目录都不再匹配。加载器只按 `<A>` 匹配，所以找不到 bundle，
什么也不做。

**诊断。** 按 `path_id`（跨版本稳定）在整个缓存里搜 mod 的目标，而不是按哈希：

```bash
grep -rl "<path_id>" "$PREFIX"/drive_c/users/*/AppData/LocalLow/Unity/ProjectMoon_LimbusCompany/*/*/__data
```

**修复。** 重定向：把 `.carra2` 里的 `<A>` 改写成真正含该目标 bundle 的目录名。注意**内层**
`<B>` 无关紧要——加载器会把 `<A>/<B>/<file>` 拍平成 `<A>/<file>`，且只按 `<A>` 取键。

注意：

- 游戏重建过的资源（例如 `sactx` 图集页）`path_id` 可能**变了**。这类按对象名（去掉结尾哈希后缀）
  加尺寸做 1:1 映射；尺寸不一致就跳过，不要硬套。
- 老格式 `.carra` 的条目没有 `.<type_id>` 后缀，加载器会把 `type_id` 当作 `-1`，跳过类型检查，
  纯按 `path_id` 替换。

## 音频 mod

**现象。** 把 `.bank` 放进了 mod 目录，但声音没变。

**检查。**

1. `log.txt` 里应对每个 bank 有 `Replacing <file>`，且文件应出现在
   `$GAME/LimbusCompany_Data/StreamingAssets/Assets/Sound/FMODBuilds/Desktop/`。
2. 比对时间戳：该目录里除了你替换的那个 bank，其余文件都应还是**装机当天**的日期。若有一批文件
   都是新的，说明另有蹊跷。
3. 同一个 `.bank` 同时只能有一个改过的版本生效——两个同名的 `.bank` mod 会互相覆盖。

**还原。** 删掉打过补丁的 `.bank`、把它的 `.bank.bak` 改回原名；或者把该 `.bank` 移出
`LimbusCompanyMods/` 再重启。

> 至于某个 bank **具体**改了什么（哪几句、哪个角色），是另一个话题，有它自己的工具坑——
> 见[文档 4](04-模组格式与取证.md#音频-bank)。
